# 설계문서 위험요소 자동 도출 에이전트

설계문서(시방서)를 입력하면, **에이전트가 스스로 위험요소 후보를 도출하고, 각 후보에 대해
과거 사고사례 DB를 직접 검색(tool calling)해서 근거를 확인한 뒤** 근거가 확인된 것만 보고서로
정리하는 프로젝트입니다.

[rag-safety-chatbot](../rag-safety-chatbot) 프로젝트(RAG 검색 챗봇)의 후속작으로, "검색+답변"
한 번으로 끝나는 RAG와 달리, **여러 단계를 스스로 판단해서 반복하는 에이전트** 구조를 구현했습니다.

## 배경

DFS(Design for Safety) 업무에서는 설계도서를 검토하며 담당자가 수작업으로 위험요소를 도출합니다.
이 과정을 "문서 분석 → 위험요소 후보 도출 → 과거 사례로 근거 검증 → 보고서 작성"이라는 에이전트
워크플로우로 자동화해봤습니다.

## 아키텍처 — Tool Calling 기반 에이전트 루프

```
[설계문서 입력]
       │
       ▼
GPT가 문서를 읽고 공정별 위험요소 후보를 스스로 판단
       │
       ▼
GPT가 "이 후보, 검색해봐야겠다" 판단 → search_accident_cases 도구 호출 (여러 번 반복)
       │                                        │
       │              ┌─────────────────────────┘
       │              ▼
       │     하이브리드 검색(벡터+BM25)으로 사고사례 DB(1,594건)에서 근거 조회
       │              │
       │◄─────────────┘ (검색 결과를 GPT에 반환)
       ▼
GPT가 모든 검색 결과를 종합해 최종 보고서 작성
(근거를 못 찾은 후보는 "제외된 후보"로 별도 표기)
```

일반 RAG는 "검색 1번 → 생성 1번"으로 끝나지만, 이 에이전트는 **GPT가 스스로 몇 번을, 어떤
질의로 검색할지 판단하고 반복**합니다 (OpenAI function calling 사용, [src/agent.py](src/agent.py)).

## 핵심 발견: 근거 정확도는 검색 품질에 좌우된다

처음에는 이 프로젝트의 검색 도구를 **순수 벡터 검색**으로만 구현했는데, 실제 인용된 근거를
원본 데이터와 대조해보니 **6건 중 2건만 실제로 일치**했습니다. 예를 들어 "발파 후 가스 농도
측정 실패"라는 위험요소에 대해, 에이전트는 실제로는 **낙석(암석 낙하) 사고 사례(id=214)**를
근거로 제시했습니다 — 유사도 점수는 높았지만 사고 메커니즘 자체가 달랐습니다.

이는 [rag-safety-chatbot](../rag-safety-chatbot) 프로젝트에서 이미 확인했던 문제(순수 벡터
검색은 전문용어/정확한 상황 매칭에 약함)가 **에이전트의 "근거 신뢰성"에도 그대로 이어진다는
뜻**이었습니다. 같은 프로젝트에서 검증했던 **하이브리드 검색(벡터+BM25)**을 이 검색 도구에도
동일하게 적용한 결과:

| | 순수 벡터 검색 | 하이브리드 검색 (벡터+BM25) |
|---|---|---|
| 검색 점수 범위 | 0.41 ~ 0.56 | 0.77 ~ 1.00 |
| 실제 내용 일치 (6건 중) | 2건 | 5건 |

프롬프트를 "검색 결과를 곧이곧대로 믿지 말고 내용을 검증하라"고 강화하는 것만으로는 한계가
있었고, **검색 자체의 품질을 개선하는 것이 근본적인 해결책**이라는 걸 확인했습니다.
(자세한 검증 과정은 커밋 히스토리 참고)

## 안전장치

- 시스템 프롬프트에서 "근거 사례의 실제 사고 메커니즘과 위험요소 후보가 일치해야 함", "사례
  하나를 여러 위험요소에 재사용 금지"를 명시해 환각을 추가로 억제
- 근거를 찾지 못한 위험요소 후보는 보고서 본문이 아니라 별도 "제외된 후보" 섹션으로 분리 —
  걸러진 항목이 있다는 것 자체가 이 시스템이 정직하게 동작한다는 증거

## 실행 방법

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# .env 파일에 OPENAI_API_KEY=sk-... 입력

python src/build_index.py      # 임베딩 인덱스 + BM25 코퍼스 생성 (rag-safety-chatbot과 동일 데이터 재사용)
streamlit run app.py           # 웹 UI 실행

# 또는 CLI로 직접 실행
cat data/sample_docs/tunnel_spec.txt | python src/agent.py
```

## 데이터

[rag-safety-chatbot](../rag-safety-chatbot) 프로젝트와 동일한 국토안전관리원 공공데이터
(철도/교량/터널 사고사례 1,594건)를 재사용했습니다.

## 향후 개선 방향

- 위험등급(상/중/하) 판단 기준을 유사 사례 건수·심각도에 따라 더 명확히 규칙화
- 근거-주장 정합성을 LLM 판단에만 맡기지 않고, 인용 문장과 사례 원문 간 별도 유사도 검증 단계 추가
- 여러 설계문서를 한 번에 배치 처리하는 기능
