# 설계문서 위험요소 자동 도출 에이전트

설계문서(시방서)를 입력하면, **에이전트가 스스로 위험요소 후보를 도출하고, 각 후보에 대해
과거 사고사례 DB를 직접 검색(tool calling)해서 근거를 확인한 뒤** 근거가 확인된 것만 보고서로
정리하는 프로젝트입니다.

[rag-safety-chatbot](../rag-safety-chatbot) 프로젝트(RAG 검색 챗봇)의 후속작으로, "검색+답변"
한 번으로 끝나는 RAG와 달리, **여러 단계를 스스로 판단해서 반복하는 에이전트** 구조를 구현했습니다.

## 배경

DFS(Design for Safety) 업무에서는 설계도서를 검토하며 담당자가 수작업으로 위험요소를 도출합니다.
이 과정을 "문서 분석 → 위험요소 후보 도출 → 과거 사례로 근거 검증 → 보고서 작성"이라는 에이전트
워크플로우로 자동화해봤습니다.

## 아키텍처 — Tool Calling 기반 에이전트 루프

```
[설계문서 입력]
       │
       ▼
GPT가 문서를 읽고 공정별 위험요소 후보를 스스로 판단
       │
       ▼
GPT가 "이 후보, 검색해봐야겠다" 판단 → search_accident_cases 도구 호출 (여러 번 반복)
       │                                        │
       │              ┌─────────────────────────┘
       │              ▼
       │     하이브리드 검색(벡터+BM25)으로 사고사례 DB(1,594건)에서 근거 조회
       │              │
       │◄─────────────┘ (검색 결과를 GPT에 반환)
       ▼
GPT가 모든 검색 결과를 종합해 최종 보고서 작성
(근거를 못 찾은 후보는 "제외된 후보"로 별도 표기)
```

일반 RAG는 "검색 1번 → 생성 1번"으로 끝나지만, 이 에이전트는 **GPT가 스스로 몇 번을, 어떤
질의로 검색할지 판단하고 반복**합니다 (OpenAI function calling 사용, [src/agent.py](src/agent.py)).

## 핵심 발견: 근거 정확도는 검색 품질에 좌우된다

처음에는 이 프로젝트의 검색 도구를 **순수 벡터 검색**으로만 구현했는데, 실제 인용된 근거를
원본 데이터와 대조해보니 **6건 중 2건만 실제로 일치**했습니다. 예를 들어 "발파 후 가스 농도
측정 실패"라는 위험요소에 대해, 에이전트는 실제로는 **낙석(암석 낙하) 사고 사례(id=214)**를
근거로 제시했습니다 — 유사도 점수는 높았지만 사고 메커니즘 자체가 달랐습니다.

이는 [rag-safety-chatbot](../rag-safety-chatbot) 프로젝트에서 이미 확인했던 문제(순수 벡터
검색은 전문용어/정확한 상황 매칭에 약함)가 **에이전트의 "근거 신뢰성"에도 그대로 이어진다는
뜻**이었습니다. 같은 프로젝트에서 검증했던 **하이브리드 검색(벡터+BM25)**을 이 검색 도구에도
동일하게 적용한 결과:

| | 순수 벡터 검색 | 하이브리드 검색 (벡터+BM25) |
|---|---|---|
| 검색 점수 범위 | 0.41 ~ 0.56 | 0.77 ~ 1.00 |
| 실제 내용 일치 (6건 중) | 2건 | 5건 |

프롬프트를 "검색 결과를 곧이곧대로 믿지 말고 내용을 검증하라"고 강화하는 것만으로는 한계가
있었고, **검색 자체의 품질을 개선하는 것이 근본적인 해결책**이라는 걸 확인했습니다.
(자세한 검증 과정은 커밋 히스토리 참고)

## 정량 평가 (에이전트 인용 재현율)

수동 검증 외에, 자동화된 평가셋도 구축했습니다 ([build_agent_eval.py](src/build_agent_eval.py),
[evaluate_agent.py](src/evaluate_agent.py)):

1. 실제 사고사례 15건을 샘플링해, GPT로 "사고가 나기 전 시방서에 있었을 법한" 담담한 작업
   절차 문장으로 역변환 (위험/사고라는 단어는 제거)
2. 15개 문장을 하나의 합성 시방서로 합쳐 에이전트에 통째로 입력
3. 최종 보고서에 **원본 사례 ID가 근거로 정확히 인용됐는지** 확인 → **인용 재현율(Citation Recall) 33.3% (5/15)**

이 수치는 앞서 수동 검증한 "6건 중 5건 정확"보다 낮은데, **다른 것을 측정하기 때문**입니다.
수동 검증은 "인용한 근거가 실제로 타당한가"를 봤고, 이 평가는 "**정확히 그 원본 사례**를
인용했는가"를 봅니다. DB에 비슷한 사례가 여러 건 있으면(예: 넘어짐 사고가 여러 건), 에이전트가
다른 타당한 사례를 인용해도 이 지표에서는 "미스"로 집계됩니다. 또한 위험요소 15개를 한 번에
분석하다 보니, 개별 검색 질의가 단일 문서를 볼 때보다 다소 일반화되는 경향도 관찰했습니다.

즉 이 지표는 "근거가 말이 되는가"보다 엄격한 "원본 소스 복원율"이라, 실제 활용 가치를
과소평가할 수 있습니다. 다만 두 지표 모두 낮게 나오는 사례가 겹친다면 그건 진짜 개선이
필요한 지점이라는 뜻이라, 두 가지를 함께 참고하는 것이 좋습니다.

## 안전장치

- 시스템 프롬프트에서 "근거 사례의 실제 사고 메커니즘과 위험요소 후보가 일치해야 함", "사례
  하나를 여러 위험요소에 재사용 금지"를 명시해 환각을 추가로 억제
- 근거를 찾지 못한 위험요소 후보는 보고서 본문이 아니라 별도 "제외된 후보" 섹션으로 분리 —
  걸러진 항목이 있다는 것 자체가 이 시스템이 정직하게 동작한다는 증거

## 위험등급 산정 데이터화

처음에는 "위험등급(상/중/하)"을 LLM이 감으로 판단했는데, 이를 **원본 데이터의 실제 사망자/부상자
통계 기반**으로 바꿨습니다 ([enrich_severity.py](src/enrich_severity.py)). 원본 공공데이터
CSV에서 각 사례의 사망자/부상자 수를 다시 매칭해, 사망자가 있으면 "상", 부상자만 있으면 "중",
피해가 없으면 "하"로 결정론적으로 계산한 뒤 검색 결과에 포함시킵니다. 에이전트는 이 값을
그대로 사용하고, 위험등급 옆에 근거(예: "근거 사례 사망자 1명")를 명시하도록 프롬프트에
강제했습니다 — 등급 판단 근거를 LLM의 주관적 추측이 아니라 실제 데이터로 대체했습니다.

## 저감대책과 2차 위험요소

실제 DFS(Design for Safety) 업무는 위험요소 도출에서 끝나지 않고, 그에 대한 **저감대책**까지
마련해야 합니다. 이 프로젝트는 각 위험요소마다:

1. **저감대책**: 유사 사고사례의 재발방지대책을 참고해 작성
2. **저감대책 적용 후 2차 위험요소**: 그 저감대책 자체가 새로 유발할 수 있는 위험을 검토
   (예: "신호수 배치"라는 저감대책 → "신호수가 장비 사각지대에서 협착될 위험"이라는 2차 위험)

을 함께 생성합니다. 2차 위험요소는 과거 사례에 명확히 기록돼 있지 않은 경우가 많아, 근거를
찾으면 사례를 인용하고 **못 찾으면 "(전문가 판단, 사례 근거 없음)"이라고 명시**해 사실(과거
사례 기반)과 추론(전문가 판단)을 섞지 않고 구분합니다.

## 실행 방법

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# .env 파일에 OPENAI_API_KEY=sk-... 입력

python src/build_index.py      # 임베딩 인덱스 + BM25 코퍼스 생성 (rag-safety-chatbot과 동일 데이터 재사용)
python src/enrich_severity.py  # (선택) 원본 CSV에서 사망자/부상자 통계 매칭 — rag-safety-chatbot의 raw CSV 필요
streamlit run app.py           # 웹 UI 실행 (텍스트 붙여넣기 또는 PDF 업로드)

# 또는 CLI로 직접 실행
cat data/sample_docs/tunnel_spec.txt | python src/agent.py

# 정량 평가 재현
python src/build_agent_eval.py   # 평가셋 생성 (이미 생성돼 있으면 생략)
python src/evaluate_agent.py     # 인용 재현율 측정
```

## 근거-주장 자동 재검증

에이전트가 스스로 "내용이 맞는지 검증하라"고 프롬프트에 명시해도 완벽하지 않기 때문에,
보고서 생성 후 **별도의 독립적인 LLM 호출로 각 위험요소-근거사례 쌍을 다시 검증**합니다
([verify.py](src/verify.py)). "인용된 사례 내용이 주장된 위험요소를 실제로 뒷받침하는가"만
판단하는 전용 프롬프트를 써서, 생성 단계의 판단과 별개로 한 번 더 걸러냅니다.

실제로 돌려보면 이 자동 검증기는 수동 검증(사람이 직접 대조)보다 **더 엄격하게** 판단하는
경향이 있었습니다 (예: 수동 검증 시 6건 중 5건 타당 → 자동 검증기로는 더 낮게 나옴). 이는
검증 LLM이 "동일 사고 메커니즘"의 기준을 사람보다 좁게(거의 동일한 절차·도구까지) 잡기
때문으로 보입니다. 그래서 이 기능은 **"최종 판정"이 아니라 "사람이 재확인할 항목을
우선순위화하는 스크리닝 도구"**로 UI에 명시했습니다 — 자동화가 사람의 최종 확인을
대체할 수 없다는 걸 확인한, 이 프로젝트 전체를 관통하는 결론이기도 합니다.

## PDF 업로드 및 보고서 내보내기

- **PDF 업로드**: 실제 시방서는 텍스트가 아닌 PDF로 존재하는 경우가 많아, `pypdf`로 PDF에서
  텍스트를 직접 추출해 입력할 수 있게 했습니다 ([app.py](app.py)).
- **Excel 내보내기**: 에이전트가 생성한 마크다운 보고서를 파싱해([report_export.py](src/report_export.py))
  공정/위험요소/위험등급/근거사례/저감대책/2차위험요소 열을 가진 위험성평가표 형식 Excel
  파일로 바로 다운로드할 수 있습니다. 화면에서 보는 데서 끝나지 않고 실제 DFS 보고서
  작성에 바로 옮겨 쓸 수 있도록 완결성을 높였습니다.

## 향후 개선 방향

- 위험요소를 한 번에 여러 개 분석할 때 검색 질의가 일반화되는 경향 완화 (문서를 공정 단위로 나눠 순차 처리하는 방식 검토)
- 여러 설계문서를 한 번에 배치 처리하는 기능
- 자동 검증기 자체의 판정 기준을 사람 판단과 비교해 튜닝 (검증기가 과도하게 엄격한 경향 완화)
